# PR21 测试用例 — feat(mini-staff): 店长 M1（满班率 + 待办）

环境：macOS aarch64，`JAVA_HOME=/opt/homebrew/opt/openjdk@21`，Maven 3.9.x。无 Docker。`dev` profile 用 H2 且 Flyway=false；库存/支付/待办走内存仓。不绑定 8080（`RANDOM_PORT`）。

设计文档 §1 角色与页面 要求「店长 M1：**完整满班率**（全日 + `byHour`）+ 待办（审批请假 / ¥500 退款 / 人工队列），不做 BI」。后端三条链路（`/f/metrics/utilization`、`/f/human-tasks` 的 approve/deny/resolve）在 PR17~PR20 已经齐了，缺的是员工端把它们拼成一屏。本 PR 补 `apps/mini-staff/pages/manager/*`，并加一条端到端报告测试把「三类待办同时在队列里 → 店长逐一出度 → 队列清空」跑通。

新增页面文件：

| 文件 | 职责 |
|---|---|
| `pages/manager/manager.js` | 语义化分组 `leave` / `refund` / `abnormal` / `queue`；满班率转柱高与色调；approve / deny / resolve |
| `pages/manager/manager.wxml` | 全日满班率大字 + 分时柱状 + 按组渲染的待办卡 |
| `pages/manager/manager.wxss` | 750rpx 设计宽：正文 ≥ 30rpx(15px)，主操作 96rpx(48px) |
| `pages/manager/manager.json` | 下拉刷新 |

`HumanTaskView` 只回 `id/taskType/title/status/orderId/bizKey`，没有分组字段，所以**分组在客户端做**：`GROUPS` 按优先级从上到下排，命中不了任何类型的落到最后一组「人工队列」（只读、线下处理），新增任务类型不会从店长台上消失。分组 key 用语义英文，不用数字编号（全局约定）。

`ManagerBoardReportTest` 除了跑接口，还对 `manager.wxss` / `manager.js` / `manager.wxml` 做静态门禁，避免后续改样式时把字号/热区改小、或把分组 key 退化成下标。

产物：`docs/test-cases/pr-21-manager-board.html`（用例表）、`docs/test-cases/pr-21-manager-m1.html`（页面预览，数据来自本次真实响应），截图 `docs/test-cases/screenshots/pr-21-manager-board.png` / `pr-21-manager-m1.png`（本机 playwright 浏览器缓存已空，改用系统 Chrome 的 `executablePath` 渲染）。

## TC-21-01 无 JWT 读满班率被拒

- **步骤**：`GET /api/v1/f/metrics/utilization` 不带 Authorization。
- **预期**：`40101`。
- **实际结果**：PASS。`code=40101`。

## TC-21-02 技师 token 没有 `order:list`

- **步骤**：用 `TokenType.T` / 角色 THERAPIST（只有 `staff:self`）读满班率。
- **预期**：HTTP 403 + `40301`。满班率是店长/前台的数据域，技师端只看自己的单。
- **实际结果**：PASS。`403 FORBIDDEN code=40301`。

## TC-21-03 全日满班率默认取今天，`byHour` 覆盖营业小时

- **步骤**：店长 token `GET /f/metrics/utilization`（不传 `date`）。
- **预期**：`date` = 今天；`byHour` 每项含 `hour` + `rateX10000`；空排班日不报错。
- **实际结果**：PASS。`date=2026-08-14 hours=12 rate=0`（demo 日历 10:00–21:45，重置后无占用）。

## TC-21-04 落单后满班率上升

- **步骤**：落 1 张散客单（P60）+ 1 张线上单（P60），再读一次。
- **预期**：`rateX10000` 从 0 上升；分母不含 `REST`（未排班/请假不进产能）。
- **实际结果**：PASS。`0 → 347`。分母 3 技师 × 48 格 = 144；分子 5 格 = 散客单 P60 的 4 格 + 1 格 buffer。线上单在造 `REFUND_APPROVE` 时已随退款请求取消并释放，所以不计入——这正是满班率该有的口径。

## TC-21-05 分时满班率能定位忙闲

- **步骤**：取 `byHour` 里的最大值与全日值比较。
- **预期**：峰值明显高于全日均值，店长才能看出哪个小时排满了。
- **实际结果**：PASS。`peak=3333 fullDay=347`——11 点这一小时 12 格里占了 4 格（33.33%），12 点还有 1 格 buffer（8.33%），其余为 0。全日均值被空闲小时摊平到 3.47%，只看全日会漏掉「11 点已经排满一个技师」。

## TC-21-06 三类待办同时在一个队列里

- **步骤**：分别造 `LEAVE_APPROVE`（`POST /a/schedule-exceptions`）、`ORDER_ABNORMAL`（散客单 → `START_SERVICE` → `POST /f/orders/{id}/abort`）、`REFUND_APPROVE`（线上单付款 + 一笔加钟支付垫到 ¥598 → `POST /f/orders/{id}/refund` 59800），然后 `GET /f/human-tasks?status=OPEN`。
- **预期**：一次查询拿到 3 条，按页面口径分别落进 `leave` / `refund` / `abnormal`，`queue` 为空。
- **实际结果**：PASS。`leave=1 refund=1 abnormal=1 queue=0`。
- **备注**：demo 项目最贵 ¥268，所以 ≥¥500 审批线必须靠加钟支付垫高，直接退 59800 会超过可退金额。

## TC-21-07 未知任务类型兜底进人工队列

- **步骤**：对一个页面没列举的 `taskType` 走分组函数；同时核对请假任务的 `bizKey`。
- **预期**：兜底到 `queue`，不丢单；`bizKey` = `leave:{exceptionId}`，店长能回溯到申请单。
- **实际结果**：PASS。`bizKey=leave:81751864529391616`。
