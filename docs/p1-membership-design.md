# P1 技术设计：会员制课包

> 状态：**P0 已实现**（课包领域 + 会员列表 + 当日时间表 + 档案编辑）
> 前置：`docs/p1-stored-card-design.md`（储值卡，与本模块并存）

## 1. 需求来源

员工端补充四条：

1. 自己的会员列表——剩余课时、累计已完成、核心问题、训练计划与完成情况
2. 所有在店老师本月耗课情况及卖课业绩排名
3. 当日时间列表，可约时间展示
4. 会员档案编辑（核心问题、测试评估、训练计划、上课后结果比对）；
   并考虑训练计划能否自动生成上课时间、到点自动提醒老师端与客户端

这不是加四个页面。原系统是「到店单次消费」，这四条描述的是「会员制课包」——
课时、耗课、训练计划、档案，原先一样都没有。

## 2. 核心决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 课包与储值卡的关系 | **两套并存，各管各的** | 储值卡存**钱**（按金额抵扣、按余额退），课包存**次数**（按次扣、按剩余次数×单价退），课包还有有效期和课程类型。合成一张表这三件事都没地方放 |
| 卖课提成与耗课提成 | **卖时记一笔，耗时再记一笔** | 卖课收的钱是**预收（负债）**，耗课才是**实现的收入**。合成一个数就分不清"这月卖得好"和"这月上得多"，而门店真正吃饭的是后者 |
| 课包 SKU | **复用 `project`**，不另开表 | 「私教60分钟」已经有时长、缓冲、价格。课包 = project × 次数 × 有效期 |
| 扣课时机 | **`COMPLETE_SERVICE` 时扣**，不是下单时 | 「耗课」的定义就是课真上完了。下单就扣的话改期和取消都要回滚，中途没来算不算耗课也说不清 |
| 训练计划自动排课 | **只生成待约，确认后才占库存** | 一次排 8 周出去那些时段就卖不掉了；会员改期是常态；自动占的单回答不了"到点人没来算不算耗课" |
| 客户端提醒 | **只推下一次，消息里引导再授权** | 见下，平台硬约束 |

## 3. 数据模型（Flyway V11）

```
member_profile      会员档案，一人一行，可编辑
member_package      持有的课包：总次数/已用/单价/有效期/卖课人
package_transaction 课时流水：PURCHASE / CONSUME / REFUND / ADJUST
training_plan       训练计划：总次数/已完成/每周频次
booking_order.member_package_id   订单绑的课包，空=按金额付的普通单
```

几个刻意的选择：

- **`member_profile` 与 `treatment_note` 并存**。前者是**当前状态**、可编辑；
  后者是**历史记录**、只增不改不删（保留 3 年）。合成一个会两头不讨好。
- **`unit_price_fen` 落库，不临时算**。除不尽时**向上取整到分**，保证
  单价×次数 ≥ 实收 —— 反过来按单价退款会退超，差额门店倒贴。
- **`training_plan.done_sessions` 由耗课累加，不手填**。手填的进度迟早跟实际上课对不上。

## 4. 分层

订单层是下层，会员域是上层，所以口子都由下层声明：

| 口 | 声明处 | 实现处 | 用途 |
|---|---|---|---|
| `SessionConsumeSide` | `order` | `membership` | `COMPLETE_SERVICE` 时扣一次课时 |
| `PackageBookingPort` | `order` | `membership` | 下单时校验课包并绑定 |
| `SlotOccupyStore.memberPackageIdOf` | `inventory` | 两个 store | 订单绑了哪张课包 |

**`PackageBookingPort` 只绑不推状态**：推 BOOKED 由 `BookingService` 自己做。
第一版让会员域去 `machine.fire()`，结果构造期循环依赖——状态机持有
`SessionConsumeSide`（就是会员服务），会员服务又要状态机，Spring 起不来。
状态机归 order 层，这条边不能反向。

**`memberPackageId` 没有塞进 `BookingOrderRef`**：那个 record 是订单的**库存视角**
（持有、床位、时段），课包属于会员域。塞进去等于把上层概念漏进库存层，
所以做成了 `SlotOccupyStore` 上的一个窄查询。

## 5. API

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/t/members?scope=` | `staff:self` | 我的会员；`scope=store` 看全店 |
| GET | `/api/v1/t/members/{id}` | `staff:self` | 详情：课包、计划、核心问题 |
| POST | `/api/v1/t/members/{id}/profile` | `staff:self` | 改档案 |
| GET | `/api/v1/t/day-slots?date=` | `staff:self` | 当日时间表 |
| POST | `/api/v1/f/packages` | `member:manage` | 前台卖课 |

老师看自己的会员走 `staff:self` 而不是新权限——那是本职工作的一部分，
不该跟"卖课、改档案"共用一个码。新增 `member:manage` 给前台和店长及以上。

**当日时间表把忙的时段也返回**。只给空档等于把老师自己的课表藏起来了，
而老师要看的是"我这一天长什么样"。

## 6. 关于第 4 条的自动提醒——平台硬约束

小程序推送只能走**微信订阅消息**，规则是**用户点一次「允许」，才能推一条**。
所以**做不到**"买了 12 次课就自动提醒 12 次"。

现实做法：

- **老师端不受限**。老师是员工，进小程序就能看到「今日待上课」，
  也可以走企业微信或短信。
- **客户端**：约课那一刻要一次授权，推**那一次**的提醒；消息里带「约下一次」
  的跳转，用户点进来再授权一次。行业通行，但**依赖用户点**。
- 想要无条件必达，只能上**短信**：要付费、要申请签名与模板报备，上线周期变长。

`notify/` 包目前是空的，这条从零开始。已按「只推下一次」定案。

## 7. 已知口子

- **不做精确预占**。约课只校验"当下还有余次"，没把"已约未上"的单算进去，
  所以同一张卡短时间连约多次可能超订，靠余次到 0 兜底。P1 补。
- **买课不走支付链路**。前台卖课只记课时，收钱走线下或储值卡。
  把买课接进微信支付是另一件事。
- **提成比例是演示值**。`MembershipPolicy` 卖课 8% / 耗课 25%，
  与 `CommissionPolicy`、`CardPolicy` 一样等运营确认。

## 8. 顺带做掉的

**主包体积超限**。加页面前主包已是 2212 KB（上限 2048），本次新增 4 页只占 48 KB，
也就是说**此前就已超 116 KB**，上传会被拒。按 `wechat-onboarding.md` 早先的预判处理：

1. **员工端拆分包**（`subPackages` root=`pages/staff`），移出 200 KB。
   员工端只依赖 `utils/`，跳转都是绝对路径，拆得很干净；
   并加了 `preloadRule`，从「我的」页预载，免得第一次点进去白屏。
2. **图片重压**（质量 75、最长边 800px），1728 → 1204 KB。
   这些图在小程序里最宽渲染到 750rpx，960px 是白扛的。

主包 **2212 → 1488 KB**，余量 560 KB。

**手机号打码挪进 `common`**。前台和会员端都要用，两份实现迟早漂移成
同一个号在两个页面显示不一样。挪的时候漏了 E164 的国码剥离，
把 `186****1111` 显示成了 `861****1111`，被前台的既有测试当场逮住。
