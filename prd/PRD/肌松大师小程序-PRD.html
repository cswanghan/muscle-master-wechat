1. 产品背景与目标

1.1 业务形态

肌松大师是「连锁门店 + 手艺人（技师）+ 预付卡」三要素叠加的到店推拿服务业务，不是单纯的预约工具。核心观察：

业务现象对应能力要求
首页三个并列入口：症状 / 门店 / 技师同一份「技师 × 时段」库存的三种检索切片
特惠卡片精确到「郑世明 · 今天19:30-20:30 · 9.5折」按 15 分钟 slot 粒度的动态定价 / 空档甩卖
技师带擅长症状标签 + 评分症状路由 + 评价体系
储值余额 + 电子/实体礼卡单用途预付费资金池，需独立账务模型
限时优惠券，限定星期/时段规则化券引擎
门店营业时间、LBS 距离、"就近"标签多门店 + 地理围栏排序

1.2 产品目标

  1. 满班率是唯一核心指标。技师工时不可库存，空一个 slot 就是永久损失。三端所有设计优先级都服务于「让 slot 卖掉」。
  2. 门店前台是交易主战场。线上预约只是入口，到店散客、加钟、临时换技师大量发生在前台，系统必须以门店为中心设计，而非只服务小程序下单路径。
  3. 资金合规优先。储值与礼卡涉及《单用途商业预付卡管理办法》，账务必须与普通订单彻底分离，不能用一张余额表笼统表示。

1.3 规模假设（容量与技术选型依据）

指标假设值
门店数首年 20 家，三年 200 家
单店技师 / 床位15~25 人 / 8~15 张
日订单单店 60~120 单，全国峰值 2 万单/日
峰值 QPS读 800，写 80（周五晚 + 大促开抢）
结论：这是低并发、高一致性要求的系统，不需要复杂分布式架构，但「不能超卖、不能算错提成、不能丢余额」的要求接近金融系统，设计与技术选型都应向可靠性倾斜。

4. 产品逻辑说明

4.1 核心资源模型：双资源约束

一次预约同时占用两个独立资源，这是整个系统最容易做错的地方：

一次服务 = 技师(1人) × 床位/房间(1间) × 时间段(N个15分钟粒度)

大量同类系统只锁技师，会出现"3 位技师都有空但店里只剩 2 张床"的超卖。必须双资源同时校验。时间粒度统一切成 15 分钟为最小单位（slot），60 分钟项目占用连续 4 个 slot；项目需预留 buffer_minutes（建议 10~15 分钟）作为换床/洗手缓冲。

库存唯一性约束

技师 slot 表与床位 slot 表均对 (资源ID, 日期, slot序号) 建唯一索引。这是最后一道防线——即使分布式锁失效、代码写错，数据库也不会让同一 slot 被两个订单占用，比任何应用层逻辑更可靠。

4.2 下单锁定流程

用户点「预约」
   → 幂等校验（requestId + 30s 防重）
   → 分布式锁 lock:slot:{技师ID}:{日期}（超时 5s）
   → 事务：校验技师 slot 全部空闲 → 择优选一间空闲床位
           → 两组 slot 置为「锁定中」，lock_expire_at = now+15min
           → 生成待支付订单
   → 延时消息（15 分钟）：到期未支付则释放
   → 返回支付参数

支付回调（需按 payment_no 唯一索引做幂等）成功后，slot 转为「已预约」，写服务记录，通知用户与技师。释放路径必须有三条兜底：延时消息到期、用户主动取消、定时任务每 5 分钟扫描超时未释放的锁定 slot——延时消息可能丢失，卡死的 slot 是直接的收入损失，兜底扫描不能省。

4.3 订单状态机

待支付 ──支付──> 已预约 ──到店──> 服务中 ──完成──> 已完成 ──> 已评价
   │                 │              │
   │超时             │取消/改约      │中止
   ▼                 ▼              ▼
 已关闭            已取消          异常单(人工介入)
                     │
                  未到店 → 爽约（计入客户信用分）

建议用状态机框架实现而非 if-else 散落各处——不完整的状态机是这类系统 bug 的主要来源。改约、加钟、换技师、退款是四个"脏流程"，需求文档常只有一行字，但占系统 80% 的复杂度，建议 P0 阶段在真实门店灰度跑顺再推广。

4.4 排班生成

技师排班模板(周维度) → 定时任务每日凌晨滚动生成第15天的 slot → 例外调整(请假/调休/跨店支援)

请假会把对应 slot 置为「休息」，若已有订单必须先走改约流程，不能直接覆盖。跨店支援时，slot 的门店归属与技师归属可以不同：报表按 slot 所属门店计算业绩，提成按技师归属店的分成规则计算。

4.5 券规则引擎

券的适用条件（星期、时段、门店、项目、职级、是否可叠加会员价、是否排除节假日等）是规则组合，必须一开始就做成规则引擎，后期硬编码改造成本极高。示例结构：

{
  "type": "CASH",            // 满减 / 折扣 / 兑换
  "face_value": 2000,        // 单位：分
  "threshold": 0,
  "rules": {
    "weekdays": [1,2,3,4,5],
    "time_ranges": [["10:00","17:00"]],
    "store_scope": {"mode":"INCLUDE","ids":[1,2,3]},
    "project_scope": {"mode":"EXCLUDE","ids":[88]},
    "therapist_level_scope": ["JUNIOR","SENIOR"],
    "stackable_with": ["MEMBER_PRICE"],
    "exclude_holiday": true
  },
  "valid": {"type":"RELATIVE","days":60},
  "issue_limit": {"per_user": 3, "total": 100000}
}

校验时机有三处，必须共用同一套求值器：领券时（是否可领）、下单选券时（是否可用）、支付时（服务端二次校验，防止前端篡改）。三处各写一份判定逻辑是长期埋雷。

4.6 技师"空档营销"逻辑

把首页特惠卡片的生成能力下放给技师本人，而非运营手工配置：

技师端看到未来空档 → 点「填满它」
  → 系统按总部锁定的折扣区间（如8.5~9.5折）供技师选择
  → 生成带技师归因的分享卡片 → 技师发给老客
  → 成交后仍计技师提成，折扣损失按规则由总部/门店/技师分摊

好处：技师有动力（空档=零收入）、老客转化率高于泛投放、归因清晰。风控手段：折扣区间由总部锁定、每周发起次数上限、仅 48 小时内空档可发起、同一客户 30 天内限享 1 次。

4.7 权限模型：功能权限 × 数据域

角色：超管 / 财务 / 运营 / 区域经理 / 店长 / 前台 / 技师
数据域：全国 → 区域 → 门店 → 个人

权限 = 功能权限 × 数据域。店长有"查看订单"功能权限，数据域限定本店；区域经理同样功能权限，数据域是名下多家门店。建议用统一注解 + ORM 拦截器在 SQL 层自动注入 store_id IN (...)，不要靠业务代码自觉过滤——那一定会漏。

敏感操作（退款 > ¥500、储值余额手工调整、券批量发放 > 1000 张、提成规则变更）全部走审批流并留痕，这正是管理后台小程序端"待我审批"的主要来源。

4.8 技师端数据可见性

  • 技师只能看到自己服务过的客户档案，不能浏览门店客户全量列表。
  • 客户手机号对技师默认脱敏（如 186****7752），联系需求走平台内消息中转，防止飞单私加微信带走客户。
  • 业绩数据只本人可见，店长可见全店。
  • 理疗记录只可增不可删，修改留痕——医疗相关记录的基本要求，也是纠纷证据。

4.9 提成规则

维度说明
钟数提成按项目 × 职级的固定金额或比例
加钟提成通常高于正常钟提成
卡销提成技师推储值/礼卡的销售提成，与钟提成分开计算
指定加成客户点名指定该技师，额外加成
折扣分摊打折订单提成基数按实收计算（否则技师会滥发折扣）
退款回滚退款时必须回滚已计提成，需支持跨月退款（本月扣回）

提成走 T+1 异步批处理而非实时计算，日终跑批生成提成流水，可重算、可审计、可追溯——实时算会在退款、改单、加钟场景下产生极难排查的对不上账。

4.10 资金账务模型

严格区分三类资金，不能混在一张余额表里：

类型性质特点
储值本金用户预付款（负债）可退，需资金存管
储值赠金营销赠送不可退，消费时按比例核销
礼卡余额预付卡可转赠，有独立卡号与状态机

采用复式记账思路：每笔资金变动写一条流水（含变动前余额/变动值/变动后余额/业务类型/业务单号），余额字段只是快照，任何时候可由流水重算校验。

合规红线：储值卡与礼卡属单用途商业预付卡，需按《单用途商业预付卡管理办法（试行）》备案；记名卡不得设有效期，不记名卡有效期不少于 3 年；系统必须支持余额可退（按未消费本金退，赠金不退）。建议立项时即拉法务确认，已发行卡后期改规则几乎不可能。

5. UED 设计说明

5.1 设计原则

  • 状态色全端统一，不可自定义：空闲=玉底色、锁定中=暖铜色、已预约=玉墨实心、异常=警示色。这套语义在客户端、技师端、后台排班视图上必须一致，否则跨端排障成本会很高。
  • 时间与金额一律等宽字体对齐，便于门店场景下的快速扫读核对。
  • 技师端三秒原则：下一单是谁、几点、在哪张床，其余信息全部折叠；技师看屏幕以秒计。
  • 无障碍适配：推拿行业视障从业者占比不低，技师端最小字号 15px、点击热区 ≥ 48px，避免纯图形按钮无文字标签。
  • 后台配置与执行分层：PC 负责配置类操作（券规则、提成规则、排班模板、退款执行），小程序端只负责看与批，避免误触成本过高的操作出现在小屏幕上。

5.2 视觉规范

色彩

  • 玉墨 #1E5C4A — 主色，用于品牌、主按钮、"已预约"状态
  • 深玉 #143F34 — 按压态、技师端顶栏
  • 暖铜 #C0803A — 价格、折扣标签、"锁定中"提示色
  • 墨 #17211D — 正文文字
  • 砂 #F4F2EE — 全端背景色
  • 警示 #B3452F — 异常单、驳回、超额退款
  • 灰 #8B948F — 次要文字与说明

字体

标题与品牌名用 Noto Serif SC 600（衬线，传递手艺感）；正文与界面文字用 Noto Sans SC 400/500；时间、金额、订单号等结构化数据统一用等宽字体，便于纵向扫读对齐。

组件与状态色块

四态时段色块贯穿客户端选时段、技师端排班、后台排班中心三处：可约锁定中已选/已预约不可约/休息

5.3 客户端关键页面设计说明

C1 预约首页

三个并列模块（特惠预约 / 门店预约 / 推拿师预约）对应同一份库存的三种切片，用户从任意入口进入都能收敛到同一张选时段页，降低流失。特惠卡片精确到单个技师单个 slot，价格用等宽字体加删除线原价强化折扣感。

C2 症状路由

按部位/按不适双路径选择，收敛到具体项目后展示"今晚可约"提示与技师承接人数，缓解决策焦虑；提供"面诊后调整项目、差价按实际结算"的兜底说明，降低选择错误的心理成本。

C3 技师详情 · 选时段

技师资质（职级、评分、服务次数、擅长标签）与 slot 日历在同一屏，日历用四态色块 + 图例，用户无需跳转即可完成"选人-选时"决策；底部悬浮价格与操作栏常驻，避免长列表滚动后丢失价格上下文。

C4 确认下单 · 支付

顶部倒计时条强化"slot 已锁定"的紧迫感，避免用户拖延导致释放；优惠明细逐项列出（券/时段折扣），金额变化可追溯，降低支付页的信任门槛。

C5 我的券包

按未使用/已使用/已过期分组；使用规则以"详情展开"形式就地呈现，而非要求用户到店才发现不可用——这是券规则引擎在前端的直接呈现，规则文案与后台配置的规则预览共用同一套生成逻辑。

C6 我的

资金总览刻意把储值余额、礼卡余额、券数量三笔分开展示，对应账务模型里三类资金不可混同的原则，即使是最基础的余额展示也要在 UI 上体现账务边界。

5.4 技师端关键页面设计说明

T1 今日工作台

深色顶栏（深玉色）与客户端浅色背景形成端别区分，避免技师误把两端截图混淆；下一单卡片信息密度刻意压低，只保留客户称呼、项目、时长、房间号、是否新客五项，其余下沉到点击后的详情。

T2 服务中 · 理疗记录

开始/结束服务用大按钮 + 计时器强化状态感，理疗记录表单默认带上次记录作为参考（力度偏好、禁忌），减少重复问诊；记录提交后不可编辑，仅可追加。

T3 空档营销

折扣区间以滑块形式限制在总部锁定范围内，技师无法超出区间自主定价；生成的分享卡片预览与客户端 C1 特惠卡片视觉一致，确保技师分享出去的内容与平台展示口径统一。

T4 业绩明细

每笔提成可下钻到具体订单，退款回滚记录单独列示并标注扣回月份，避免技师因为"钱莫名变少"产生信任危机。

5.5 管理后台关键页面设计说明

A1 数据看板

满班率作为唯一强调色（玉墨实心背景）卡片置于首位，其余指标为白底弱化展示，明确指标优先级；分时柱状图用暖铜色高亮低谷时段并直接给出"去配置"入口，将数据洞察与行动路径打通，而非停留在只读报表。

A2 排班中心

技师与床位甘特图双轨对照，拖拽改约时前端即时提示双资源冲突；请假申请与已有订单冲突时用警示色块直接嵌入排班行内，而非另开弹窗，保证处理链路不跳出上下文。

A3 订单中心

异常单整行使用警示底色置于列表中，无需筛选即可发现；采用游标分页而非跳页，避免深度分页在大数据量下的性能问题；导出走异步任务，避免阻塞界面。

A4 券规则配置

表单结构与规则引擎 JSON 字段一一对应，避免"表单能配、后端不认"的错位；提交前生成 C 端展示文案预览，让运营在配置阶段即可核对客户看到的文案是否清楚，减少上线后客诉。

M1/M2 管理后台小程序

只承载"看与批"：经营概览用深色顶栏 + 大字号满班率数字，适配移动场景下的快速扫读；审批卡片直接携带决策所需的全部上下文（冲突提示、金额、原因），减少审批人跳转查证的次数。

6. 非功能需求

6.1 性能

  • 门店/技师/项目列表缓存 5 分钟，变更主动失效。
  • 可预约时段查询是最高频接口，按门店+日期聚合缓存 30 秒，写操作主动失效——首页秒开依赖此项。
  • 分页一律用游标，后台导出走异步任务 + 消息推送结果。

6.2 可靠性

  • 支付、退款、提成三条链路的所有接口必须幂等，用业务唯一键实现，不依赖分布式锁兜底。
  • 消息队列消费幂等 + 死信队列 + 人工重投后台。
  • 资金操作每日对账：第三方支付流水 vs 系统流水，T+1 自动比对并告警。

6.3 监控告警

业务指标告警优先于技术指标：支付成功率下跌 > 5%；slot 锁定超 30 分钟未释放数量 > 10；资金流水与余额快照不一致；某门店 2 小时无订单（可能设备/网络故障）。

6.4 安全与合规

  • 手机号、地址加密存储，日志脱敏。
  • 理疗记录属健康相关敏感个人信息，需单独告知同意、最小化收集、访问全量留痕。
  • 抢购类接口加验证码 + 单用户频控。
  • 后台操作日志不可删除，保留 3 年。

9. 遗留待确认问题

  1. 是否有集团既有会员体系/CRM 需要打通？决定用户中心是自建还是对接。
  2. 是否需要上门服务（技师到家）？如需要，库存模型要加入路程时间与地理约束，复杂度上升一个量级。
  3. 医疗资质边界："对症调理"的宣传口径与实际服务范围，是否涉及医疗机构执业许可，直接影响理疗档案的合规等级。
  4. 实体礼卡的印刷、激活、防伪方案由谁承担。
  5. 是否需要对接美团/大众点评的团购券核销。
